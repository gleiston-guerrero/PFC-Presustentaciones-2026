# HU-10: Gestión de salas (RF-10)

**Prioridad MoSCoW:** Should

## Formato Connextra
> Como **coordinador o administrador**,
> quiero **registrar, listar y eliminar salas físicas o virtuales disponibles para defensas**,
> para **que el cronograma (HU-04) tenga un catálogo real de espacios donde programar cada defensa**.

## Checklist INVEST

| Criterio | Cumple | Nota |
|---|---|---|
| Independent | ✅ | Es un catálogo base, no depende de otras HUs |
| Negotiable | ✅ | Los atributos exactos de una sala (capacidad, tipo) son negociables |
| Valuable | ✅ | HU-04 depende de que existan salas registradas |
| Estimable | ✅ | CRUD simple |
| Small | ✅ | 3 endpoints (listar, crear, eliminar) |
| Testable | 🟡 | Verificable, pero sin prueba automatizada real hoy |

**Por qué es "Should" y no "Must":** en la práctica el catálogo de salas se puede sembrar una sola vez
al desplegar el sistema (como de hecho ocurre hoy: `PreSustentacionesApplication.initDemoData()` siembra
una facultad y carrera inicial) sin necesitar la funcionalidad de gestión completa día a día.

## Criterios de aceptación (Gherkin)

```gherkin
Feature: Gestión de salas
  Scenario: Registro de una sala nueva
    Given un administrador autenticado
    When envía POST /api/v1/salas con código, nombre y capacidad
    Then el sistema registra la sala como disponible

  Scenario: Eliminación de una sala sin defensas programadas
    Given una sala sin cronogramas asociados
    When el administrador envía DELETE /api/v1/salas/{id}
    Then el sistema elimina la sala
```
