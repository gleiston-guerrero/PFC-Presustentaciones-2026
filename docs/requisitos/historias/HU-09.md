# HU-09: Reportes de defensas (RF-09)

**Prioridad MoSCoW:** Could

## Formato Connextra
> Como **coordinador de carrera**,
> quiero **generar reportes estadísticos y en PDF del estado de las defensas** (por periodo, por
> carrera, por estado),
> para **tener visibilidad agregada del proceso sin revisar solicitud por solicitud**.

## Checklist INVEST

| Criterio | Cumple | Nota |
|---|---|---|
| Independent | ✅ | Es de solo lectura, agrega datos ya generados por otras HUs |
| Negotiable | ✅ | El formato de los reportes es negociable |
| Valuable | 🟡 | Útil para gestión, pero no bloquea el flujo académico de ningún estudiante individual |
| Estimable | ✅ | Alcance acotado |
| Small | ✅ | Consultas agregadas, sin lógica de escritura |
| Testable | 🟡 | Verificable, pero sin prueba automatizada real hoy |

**Por qué es "Could":** ningún estudiante o jurado depende de esta funcionalidad para completar su
propio proceso; es una herramienta de gestión para la coordinación.

## Criterios de aceptación (Gherkin)

```gherkin
Feature: Reportes de defensas
  Scenario: Reporte estadístico en JSON
    Given defensas registradas en distintos estados
    When el coordinador envía GET /api/v1/reportes/estadisticas/json
    Then el sistema responde con el conteo agregado por estado

  Scenario: Reporte en PDF
    Given un periodo académico con defensas concluidas
    When el coordinador envía GET /api/v1/reportes/cronograma/pdf
    Then el sistema genera un PDF con el cronograma consolidado
```

## Trazabilidad

- **Módulo backend:** Reportes (`ReportController`, procedimiento `sp_generar_reporte_defensas`)
- **Endpoint:** `GET /api/v1/reportes/defensas`, `GET /api/v1/reportes/estadisticas/json`
- **Prueba automatizada real:** ❌ Sin prueba dedicada
- **Evidencia empírica adicional:** k6 Load Test (el endpoint de reportes se ejercitó indirectamente en las corridas de carga documentadas en [`../../../k6/README.md`](../../../k6/README.md), aunque no como prueba funcional dedicada)
