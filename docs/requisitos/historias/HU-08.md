# HU-08: Notificaciones a usuarios (RF-08)

**Prioridad MoSCoW:** Could

## Formato Connextra
> Como **usuario del sistema**,
> quiero **recibir notificaciones sobre cambios de estado en mi proceso** (solicitud aprobada, jurado
> asignado, cronograma programado, evaluación registrada),
> para **enterarme sin tener que consultar manualmente el sistema todo el tiempo**.

## Checklist INVEST

| Criterio | Cumple | Nota |
|---|---|---|
| Independent | ✅ | Es una capa transversal que se dispara desde otras HUs, pero se puede probar de forma aislada |
| Negotiable | ✅ | El canal (in-app vs. email) es negociable |
| Valuable | 🟡 | Mejora la experiencia, pero el flujo académico funciona sin ella (consulta manual) |
| Estimable | ✅ | Alcance acotado |
| Small | ✅ | CRUD simple de notificaciones + marcado de leídas |
| Testable | 🟡 | Verificable, pero sin prueba automatizada real hoy |

**Por qué es "Could":** es una mejora de experiencia de usuario, no bloquea el flujo académico crítico
(un estudiante puede simplemente consultar el estado de su solicitud manualmente).

## Criterios de aceptación (Gherkin)

```gherkin
Feature: Notificaciones
  Scenario: Notificación automática ante cambio de estado
    Given una solicitud a la que se le asigna un jurado
    When la asignación se completa
    Then el sistema crea una notificación para el estudiante y para cada jurado asignado

  Scenario: Marcar notificaciones como leídas
    Given un usuario con notificaciones no leídas
    When envía PATCH /api/v1/notificaciones/usuario/{id}/marcar-todas-leidas
    Then todas sus notificaciones pasan a estado leído
```
